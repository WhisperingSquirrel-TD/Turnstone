## 3. Non-negotiable principles [M]
1. Server holds the only true state; clients send commands and render views.
2. Every response and socket message built by one projection, viewFor(viewer, state), with an allow-list per viewer type. Never send secrets and hide them with CSS.
3. Uniform interaction: at every private moment every living player's device shows the same layout, colours, number of options, text length band, sound, vibration and minimum time. Faithful answer a decoy question while Traitors choose a victim. A bystander or someone timing taps learns nothing.
4. Shield first: secrets only behind the privacy shield and hold-to-reveal (section 10); never in notifications, titles, URLs, history, favicons, theme colours, storage, logs or analytics.
5. The playing coordinator is blind: logistics only; no route, screen or export shows roles, murder choices or unrevealed votes to anyone not entitled, including admins. Optional all-seeing host mode only if every player is told on joining.
6. Fairness: cryptographically secure randomness; publish a SHA-256 commitment of the deal plus salt; reveal both at the end.
7. Built for real homes: patchy Wi-Fi, locking phones, reloads and early leavers are normal.
8. Website only [Owner]; installed app mode optional.
9. WCAG 2.2 AA, child and older-adult options, ways to play without your own phone.
10. Guests need only a display name and seat PIN.

## 4. Tech stack, architecture, deployment [M]
TypeScript strict, pnpm workspaces. Engine: pure deterministic game logic, no I/O, injected clock and random source, event-sourced (domain, commands, events, projections, planner). Shared: zod schemas for every command, event, view and API payload; UK English locale strings. Server: Node LTS, Express, Socket.IO, PostgreSQL via Drizzle with committed migrations, durable deadline scheduler polled every second or pg-boss, never in-memory timers alone. Web: React, Vite, React Router, Tailwind, TanStack Query; public pages prerendered to static HTML; game, coordinator console, presenter, admin. Sign-in: maintained OIDC/OAuth library (Better Auth, Auth.js or Passport with openid-client), recorded in DECISIONS.md. Tests: Vitest, fast-check, Supertest, socket.io-client, Playwright, axe-core, Lighthouse CI. Logs: pino with redaction. Docs: SPEC, PLAN, DECISIONS, PROGRESS, PRIVACY, MANUAL_TESTS, SCENARIO_REPORT, LAUNCH.
Realtime: commands via HTTPS POST with idempotency key, returning the new state version. After any change the server pushes each viewer their own fresh view through a private Socket.IO room joined only by the server after authentication. On reconnect, pageshow or visibility change the client re-fetches its view. Whole views, not diffs.
Persistence: append-only event log per game (seq, type, payload, timestamp) is the source of truth; rebuild by replay with snapshots. Deadlines stored as absolute UTC timestamps.
Deployment (later, owner's decision): Reserved VM, single instance; Autoscale breaks WebSockets and the scheduler. /healthz and /readyz. Secrets: DATABASE_URL, SESSION_SECRET, APP_BASE_URL, ADMIN_EMAILS, GOOGLE_CLIENT_ID/SECRET, LINKEDIN_CLIENT_ID/SECRET, FACEBOOK_APP_ID/SECRET; optional MICROSOFT_CLIENT_ID/SECRET, APPLE_CLIENT_ID/TEAM_ID/KEY_ID/PRIVATE_KEY, VAPID keys, INDEXNOW_KEY, SENTRY_DSN. Separate dev and prod redirect URIs. Multi-instance out of scope.

## 5. Game engine [M]
decide(state, command, ctx) returns events or a rejection; evolve(state, event) returns the next state; ctx supplies time and randomness.
Phases (neutral code names; themes supply wording): DRAFT; LOBBY (join, device check); DEAL (roles dealt, private reveal, acknowledge); repeated cycle in configurable order, default MISSION, DEBATE, VOTE, VERDICT, SHADOW, DAWN. MISSION: real-world or in-app challenge, results recorded, pot and powers awarded. DEBATE: timed discussion. VOTE: secret simultaneous phone ballots. VERDICT: votes revealed, one banished, role revealed per config, recruitment may follow. SHADOW: private moment for all; Traitors choose a victim, others answer a decoy. DAWN: murder announced, or that no one was taken. ENDGAME: alternating FINAL_VOTE (end or continue) and FINAL_BANISH. FINISHED: full reveal, awards, recap. ARCHIVED: read-only, then deleted per retention. PAUSED overlays any phase and freezes deadlines.
Advancing: by the coordinator, at a scheduled time, or when all required actions are done and a minimum time has passed; configurable per phase.
Commands (zod-validated, idempotency key; coordinator commands carry the expected version): CreateGame, UpdateConfig, JoinGame, ApproveSeat, MergeSeats, PairSeat, SetSeatLeaveTime, LockLobby, StartGame, AcknowledgePrivate, RequestRedeal, SubmitShadowChoice (victim or decoy, same shape), PostTraitorMessage, SubmitVote, RecordMissionResult, AllocatePower, RespondToRecruitment, SubmitEndgameVote, SubmitGhostPrediction, AdvancePhase, ExtendPhase, ShiftSchedule, Pause, Resume, MarkDeparted, TransferCoordinator, ResetSeatPin, EndGameEarly.
Win checks after every elimination or departure: no Traitors alive and no sleeper waiting means the Faithful win; Traitors alive at least equal to Faithful alive, with the parity rule on, means the Traitors win; two players alive ends the game, and any Traitor among them wins; an endgame vote to end gives the whole pot to surviving Traitors, otherwise the surviving Faithful share it.
Invariants (property-tested): exactly one role per seat; Traitor count at the deal matches config; eliminated or departed seats cannot act except via ghost features; no self-votes; Traitors cannot target Traitors; protected seats cannot be murdered; every game ends within a computed maximum number of steps; replay reproduces identical state; viewFor never exposes a field outside its allow-list.

## 7. Schedule planner [M][Owner]
Turns seats and a time window into an editable timetable, from one hour to two weeks. Inputs: N seats, T Traitors, F final size, start and end, blocked windows (meals, events, travel), quiet hours, seat leave times (such as a child's bedtime), step durations.
Method: E = N minus F eliminations; a standard cycle removes two (one murder, one banishment); C = E divided by 2 rounded up, with a banishment-only half-cycle for an odd remainder. Never schedule inside blocked windows or quiet hours; place DAWN near natural gatherings. If it does not fit, compress in this order: shorten debates to minimum; drop missions after cycle 1; double banishment; double murder; raise F by one. With spare time, extend: longer debates, extra missions, a murder-free night with forced recruitment, the seer. Return three options (Relaxed, Standard, Compressed), each with a timetable, expected players left after each step, and warnings.
Default minutes (Quick / Day / Multi-day): Deal 3 / 10 / open 12 hours; Shadow 2 / 15 / overnight; Dawn 1 / 5 / breakfast; Mission 5-8 / 20-45 / async up to a day; Debate 6 / 15 / 30 or async thread; Vote 2 / 3 / 10; Verdict 2 / 5 / 5; Endgame 10 / 30 / 45.
Formats: Quick: one room, manual or auto advance, missions optional, Traitors confer by chat. Day: hybrid advance around fixed events, the presenter gathers people, private moments announced minutes ahead. Multi-day: players may be apart, every step works remotely, shadow overnight, async debate threads, opt-in notifications, daily summary.
Acceptance example: N=15, T=3, F=4, 10:00 to 21:00, blocked 13:00-14:30 and 15:00-15:15. A valid Standard plan: 10:00 deal and device check (15 alive); 10:30 mission 1; 11:30 debate, vote, verdict (14); 12:15 shadow, dawn 12:55 (13); 14:30 mission 2 with shield; 15:15 round table (12); 16:00 shadow, dawn 16:30 (11); 17:00 mission 3 and round table (10); 18:15 shadow, dawn 18:45 (9); 19:00 round table (8); 19:30 shadow, dawn 19:45 (7); 20:00 double banishment (5); 20:20 shadow, dawn 20:30 (4); 20:30 endgame, done by 21:00. Also test 5 and 40 seats, 1-hour and 14-day windows, too-short windows (clear error with the minimum time needed), mostly-blocked days, clock changes and leave times.

## 8. Roles, powers, twists
Faithful [M]: votes; answers decoys in shadow. Traitor [M]: knows the other Traitors, chooses victims, private chat, votes. Sleeper [S]: a Faithful secretly pre-selected at the deal, unaware; activated through a normal private moment if all Traitors are gone before the endgame; Traitors never told. Recruited Traitor [M]: accepted an offer; immediate Traitor powers; sees chat only from that point.
Recruitment [M]: Traitors pick a target in shadow. At the next private moment every living non-Traitor sees a screen; only the target sees the offer, everyone else a same-shaped decoy. Offer rules: decline keeps the target Faithful and the Traitors are told. Ultimatum rules: decline means murder at the next dawn.
Shield [M]: protects from the next murder only; if targeted, no death, dawn says no one was taken, Traitors privately told the target was protected. Secret allocation [M]: the blind coordinator records mission winners; the server picks one at random or runs a private vote among them and tells the holder privately. Double vote [C]: next vote counts twice, shown in reveal. Seer [C]: at the endgame threshold one player learns one other's role. In-person murder [C]: Traitors hand over a physical token before a deadline; victim confirms in the app.

## 9. Joining, seats, devices, recovery [M]
Invites: unguessable join link (at least 128 bits), six-character code from an unambiguous alphabet, QR on the coordinator's phone and the presenter. Short-code joins need coordinator approval and are rate-limited. Guest join: display name 2 to 20 characters, filtered and unique in the game; generated initials avatar; 4 to 6 digit seat PIN; accessibility choices (tap instead of hold, large text, simple language); no email, phone or account. Signed-in join links to history. A seat is one role and vote, with one or two people and one or more devices. Shared device pass-and-play: after each action, back to "Pass the device" with a seat picker; PIN per seat; nothing private kept in memory or on the page once locked. Lobby: approve, rename, merge duplicates, remove, pair, set leave times, lock. Device check for everyone before the deal: a practice private moment with a harmless card, connection check, wake lock, house rule (no screenshots, no peeking); deal blocked until all pass or the coordinator overrides. Recovery: game code, name and PIN on the new device; old device leaves the seat; public log and presenter show "[Name] moved to a new device". Forgotten PIN: coordinator reset, publicly announced, needs co-coordinator approval if one exists. 5 failed PIN attempts lock the seat for 15 minutes and alert the coordinator.

## 10. Privacy shield and hold-to-reveal [M][Owner]
Sequence: (1) Every living player's screen switches at the same moment to a full-screen "Shield your screen" card with a 5-second countdown; the presenter shows "Private moment: shield your phones"; identical vibration on Android; the same soft tone if sound is on. (2) The player taps "I'm shielded". (3) A large hold pad; content appears only after the finger is held for the hold time (500 ms, filling ring) and only while held. (4) Hide instantly on release, pointercancel, finger leaving the pad, page hidden, blur, pagehide, orientation change, or the per-hold limit (10 s, then lift and hold again). (5) Choices (vote, victim, decoy, recruitment answer) appear while held and need a second deliberate confirm; otherwise "Done". (6) The same minimum duration for every player.
Rules: fetch secrets only when the hold begins, render only while held, remove from the DOM on release; never in the DOM, localStorage, sessionStorage, IndexedDB, service worker cache or URL. Identical layout for every role: background, card size, fonts, colours, button count, text length band; no role-specific colour. Faithful get a decoy question during shadow with the same number of options as the Traitors' screen, such as "Who do you suspect most right now?"; store decoy answers for awards. Revealed text at moderate size and contrast (large text mode overrides). Disable selection, long-press menus and dragging; no scrolling while held. Title, favicon and theme-color never change during private moments. On visibilitychange, cover content before the app-switcher snapshot. Screenshots cannot be blocked; the device check states the rule.
Accessibility: tap mode (reveals for up to 5 s); screen reader mode ("Reveal privately" reads via a polite live region, then removes it; suggest headphones); paired seats reveal together.
Tests: Playwright on WebKit and Chromium mobile: absent before hold, present after hold time, absent after release, pointercancel, page hide and time limit; no secret in DOM snapshots, storage or URL outside a hold; identical bounding boxes and computed colours for Traitor and Faithful screens.

## 11. Coordinator console, presenter, ghosts [M]
Console, phone-first: phase, countdown, next step; advance, extend by 1, 5 or 15 minutes, pause, resume, shift the remaining schedule. During private moments, progress as counts only ("11 of 14 done"); names only for public steps. Record mission results, award public shields, manage seats (departed, late joiners, leave times, PIN resets), transfer rights, end early with confirmation. Undo the last coordinator action within 60 s if no private information has been released since. Every coordinator action appears in a public log all players can read. Coordinator offline 2 minutes when an action is needed: co-coordinator prompted; with none, any player can request takeover, approved by a majority of living players.
Presenter (/tv on any browser, paired by code): public information only: lobby QR and names, timetable, countdowns, private-moment warnings, dawn announcements and verdicts (brief animation respecting reduced motion), one-by-one vote reveals and tallies, missions, timers, scores, pot, endgame, final reveal, awards, "Built by Stackstone Consulting". Speech-synthesis narration mirrored by text, "Tap to enable sound". Room-readable type, landscape, wake lock.
Ghosts: public log and timetable; mission referee tools when enabled (coordinator confirms); prediction league; a separate ghost chat; their finale say per config; no secrets unless the spectator option is on.

## 12. Missions, pot, endgame, recap
Mission library [M]: seed at least 24 original missions as admin-editable data: title, category (general party, office, outdoor, seated and accessible, remote-friendly, children, optional seasonal packs), players, duration, materials, set-up, rules, scoring, maximum pot value, accessibility notes. Coordinators can add their own. Ideas: blind build, straight face, blind taste test, charades relay, spoon pass, memory tray. In-app missions [S]: a phone quiz or poll scored by the server, the fairest way to award secret shields. Pot [M]: each mission has a maximum; the coordinator records earnings; never below zero; display unit only; no money handled.
Endgame [M]: remaining players vote privately to end or banish again; meeting the end rule ends the game; otherwise a round-table banishment without role reveal by default, then repeat; at two players the game ends automatically. Results: any surviving Traitor shares the whole pot; otherwise surviving Faithful split it. Full reveal: every role, murder choice, vote, recruitment and shield, plus the fairness check (commitment, salt, verification). Awards [S] from votes and decoys: sharpest detective, best poker face, most wrongly accused, ghost prediction champion. Recap [M]: participant-only timeline by default, shareable image with first names only, "Run your own game" and "Team-building with Stackstone" calls to action, never indexed.

## 18. Test strategy and full-game scenario testing [M][Owner]
No release reaches players until many thousands of complete games, covering every interaction of any three settings, run cleanly through the engine, the real server and real browser engines. Every literal combination is billions, so use layers.
Layers: engine unit tests (every command's success and rejection); fast-check properties (section 5 invariants); planner table tests; no-leak; API and socket contract tests (zod, idempotency, versions, reconnect, room isolation); authorisation matrix; scheduler with a fake clock (deadlines, pause, shift, restart); security (CSRF, headers, cookies, rate limits, PIN lockout, OAuth state and nonce mismatch against a local test identity provider); Playwright end-to-end on phone, tablet and desktop profiles in browser and installed-app modes; axe on every screen; public site raw-HTML and Lighthouse CI; load [S] 50 concurrent 15-seat games with 95th percentile command latency under 300 ms.
Full-game scenario testing: (1) One typed parameter model of every rule-affecting setting with the wizard's constraints, shared by tests and wizard. (2) Exhaustive core sweep: every seat count 5 to 40, times every valid Traitor count, times every format, as complete games with different seeds and bot strategies. (3) A 3-way covering array over all rule-affecting settings honouring constraints, plus 2-way at 30 to 40 seats; each row played as complete games; record the generator in DECISIONS.md. (4) Random fuzzing including illegal commands, disconnects, departures, pauses, time-outs and late joins. (5) Differential check against a small, separately written reference implementation of the rules: eliminations, winners and pot must match. (6) At least 40 golden scenario YAML files describing complete games with expected outcomes: one per section 17 edge case, the section 7 example and each format; readable enough for non-developers to add more. (7) Bots: random; cautious Faithful; aggressive Traitors; Traitors who never act; non-voters; serial disconnectors; a coordinator trying to discover secrets, which must always fail. (8) After every step of every game, check: invariants, no-leak for every viewer, uniform private moments, replay equality, termination bound, pot never negative, nothing in blocked windows. (9) Full-stack games through real HTTP and sockets with 5 to 40 simulated clients, including a mid-game restart and injected faults (dropped sockets, duplicated and reordered commands, 2 s latency). (10) Playwright complete games with real browser contexts (iPhone WebKit, Pixel Chromium, iPad WebKit, desktop presenter and coordinator) plus bots, in browser and installed-app modes. (11) Soak and chaos [S]: an accelerated 12-hour day game and a 7-day multi-day game with random restarts and clock changes. (12) Mutation testing [S]: Stryker on the engine, score at least 80%. (13) Deterministic seeds; any failure saves a minimal reproduction that becomes a permanent regression test.
Commands: verify samples each suite (2 games per sweep cell, 5 per covering row, 3 full-stack games, browser smoke tests). verify:full runs at full volume (at least 20 games per sweep cell, 50 per covering row, 100,000 fuzzed games, 20 full-stack games, complete browser games on every profile), writes docs/SCENARIO_REPORT.md (games, combinations covered, timings, failing seeds) and must be green before any production deploy.
No-leak suite: a property test that viewFor returns only allow-listed fields; full-stack payload capture asserting no Faithful, ghost, coordinator or presenter payload contains another seat's role, Traitor chat, murder choices, recruitment targets or unrevealed votes before their reveal; browser runs check titles, URLs, storage and service worker caches. Uniformity suite: Traitor and Faithful screens have the same element count, bounding boxes, computed colours and minimum duration, and start in the same server event.
Release safety: rehearsal mode (an organiser plays a fast practice game with bots filling seats; doubles as the public demo); before any deploy, replay every in-progress game on the new code and abort on any difference; versioned event schema with upgraders; admin-set change-freeze dates blocking deploys except security fixes; feature flags for [S] and [C]; admin health view (active games, error and reconnect rates).
Coverage: engine at least 95% lines and 90% branches; server at least 85% lines. Manual: docs/MANUAL_TESTS.md covering a real iPhone, Android phone and tablet in browser and installed modes, VoiceOver, TalkBack, lock and unlock mid-game, battery saver, a TV presenter via casting, and a playtest with five or more people.

## 20. Scale, performance and peak days [M][Owner]
The public website is static and served from a CDN, so visitor numbers never touch the game server; the game client is tiny; the server runs thousands of games at once and can scale out. This section overrides sections 4, 16 and 18 where they conflict.
One site, app hanging off it: a single domain. Public pages are the front door; "Start a game" and "Join a game" lead to the app on the same domain; join links and QR codes go straight to the join screen. The game server handles only game traffic (API and sockets).
Public website: static files only, prerendered at build, served from a CDN or static hosting, with long-lived caching for hashed assets and short revalidated caching for HTML. No server work per page view; works with JavaScript off. Under 200 KB per page before images and under 15 KB of JavaScript; system font stack, no web fonts; images AVIF or WebP under 100 KB each, lazy-loaded below the fold.
Game client: first load of the player app under 120 KB compressed JavaScript and under 200 KB total. Coordinator, presenter, wizard and admin are separate chunks loaded only when needed. No web fonts, no images on game screens (inline SVG icons only), no third-party scripts. Usable within 3 seconds on a low-end Android phone over slow 4G; cached after the first visit. After loading, a typical view update is under 2 KB; no polling loops; socket heartbeats no more often than every 25 seconds. If React cannot meet the budget, record options in DECISIONS.md (for example Preact's compatibility layer) and ask before changing.
Game server: any instance can handle any request. Game state lives in PostgreSQL (snapshot plus recent events) and every command uses optimistic version checks, so no state exists only in one instance's memory. Real-time pushes work across instances through a Socket.IO adapter needing no extra paid service (for example the PostgreSQL adapter); Redis only with owner approval. Deadlines are claimed with row locks (FOR UPDATE SKIP LOCKED) so any number of instances can run the scheduler without double-firing. Database connection pooling; small per-game memory released when a game finishes. Scale up first (bigger VM), then out (more instances) with no code changes. Multi-instance support moves from out of scope to [S].
Capacity targets, proven by tests and reported in docs/CAPACITY.md with measured players per CPU core and per GB of memory: steady play of 1,000 concurrent 15-player games (15,000 players) on one production VM with 95th percentile command latency under 300 ms; private-moment fan-out reaching every device in a game within 1 second at the 95th percentile; a start-of-day spike of 300 games dealing within the same 5 minutes; a join storm of 5,000 joins per minute; the public site serving 1,000 requests per second with zero load on the game server; a 12-hour soak at 50% of steady capacity with no memory growth.
Peak-day protection: admission control, so above 80% of measured capacity, creating a new game shows "Busy right now, try again in a few minutes", while joining and playing existing games is never slowed or refused. Organisers can schedule games in advance; the admin dashboard forecasts load per day from scheduled games so hosting can be sized before peak days such as 25 December. Change freeze around peak days (section 18) and a public status page [S].
Free tier: fine for building and for reduced-scale load tests that measure cost per player and extrapolate. Full-scale load tests and peak-day hosting need a paid production VM and database plan, which is the owner's decision before launch.

## 22. Traitor tasks and hosting portability
Traitor tasks [M], optional per game [Owner]: small secret missions Traitors must complete in the room without being noticed. The coordinator switches them on or off at set-up.
Settings: Traitor tasks (Off, On; default Off); tasks per cycle (one each, one shared; default one each); missed-task consequence (none; Traitors lose their next murder; default lose next murder); task filters (family, office, adults only; seated; remote-friendly).
Delivery: at the first private moment of each cycle each Traitor receives a task, and every other player receives a same-shaped decoy card, such as "Keep watch today: who is acting oddly?".
Reporting: at the next shadow step every living player gets the same "Anything to report?" screen. Traitors mark their task done or missed; everyone else answers the decoy. Honour system; fellow Traitors see the report in Traitor chat. Spotting is social: players raise suspicions at the round table, with no extra mechanic.
Library: at least 40 original tasks as admin-editable reference data, tagged by setting, minimum age, accessibility and difficulty. Coordinators can add their own, filtered for offensive words. Every task must be safe, legal and kind: no touching people without consent, no pressure to eat or drink, no leaving the venue, no damage, nothing that embarrasses or targets a person. Ideas to write in your own words: get two different people to say a chosen word; move a named object to another room unnoticed; steer a conversation onto a given topic; sit in a different seat at the next gathering; make someone laugh during the round table.
Tasks are revealed in the final reveal and recap, with a "smoothest operator" award for the most completed.
Tests: included in the parameter model and covering arrays; golden scenarios for a completed task, a missed task cancelling a murder, a Traitor banished mid-task, and a new recruit receiving a task; no-leak and uniformity checks on delivery and reporting.
Hosting portability [M]: the live version may run the public website on Vercel and the game server elsewhere. The public site and app shell build to pure static output, deployable to any CDN, including Vercel, without the game server. The game server (API, Socket.IO, one-second scheduler) is a long-lived Node process deployable to any always-on host, such as a Replit Reserved VM or a container host. The API and socket origin come from config: the same origin or a sibling subdomain; cookies, CSRF, CORS and the CSP connect-src support both. No production dependency on Replit-only runtime features.
All-Vercel hosting [C]: Vercel's WebSocket support is in public beta, connections close at the function time limit (about 5 minutes), there is no built-in fan-out across instances, and free-plan cron runs only daily. Revisit when generally available; record in DECISIONS.md; do not build now. Hosting and any paid plan are owner decisions before launch.
